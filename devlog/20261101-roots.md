## What the kernel already is, measured against that

The module boundary is already the right shape and already his bus. A module is five
verbs (`name`, `init`, `handle`, `snapshot`, `restore`) and a context of about fifteen
requests: schedule and send events (topic, loosely typed JSON data, optional cell),
subscribe (optionally at cells), create ledgers and move amounts, declare stocks, report
a scalar, publish a field frame, write or read a shared world field. Events carry untyped
blobs with a handful of standard topics (`tick`, `kernel.close`, `world.write`), which is
his Orbital design. The World store is his "database handle for shared continuous data".
`sun.irradiance` is proof of his 2020s intuition: a continuous phenomenon is just a
module that publishes fields, indistinguishable at the kernel from an agent module.

Three places where it is already painting a corner, all cheap to fix now and expensive
later:

1. **Module kinds are a compiled-in list.** `esim_modules::kinds()` and `build()` match
   on thirteen strings. That is the tight single surface he names as the failure mode, at
   small scale.
2. **Modules describe nothing about themselves.** Nothing says which topics a module
   publishes or subscribes, which fields it owns or reads, which ledgers it touches, which
   data it fetches, what its parameters are. The kernel cannot check a manifest's wiring
   before a run, and an LLM has nothing to read but Rust source.
3. **Place is repeated per module.** The M10 manifest states the Boone bounding box and
   resolution five times. A manifest should say the place once.

## Proposals, in the order they should land

### 1. The module contract becomes a protocol, not only a Rust trait

Keep the trait as the in-process form. Define the same five verbs and fifteen requests as
a versioned wire protocol (JSON lines over stdio or a socket; events in, requests out,
snapshot as a blob). Then a module can be, interchangeably: compiled in; a wasm component
(the brief's loader); a separate process in any language; or a container. The kernel does
not care which. Fortran behind BMI, a Python crop model, someone else's Rust, all plug in
without touching the kernel. The protocol is small enough to print on a page, which is
what makes it resilient: the bus blob stays loosely typed, the standard topics stay few,
and the thing that is actually versioned is the vocabulary (field names, units, ledger
names, topic names).

### 2. The zoo: modules addressed by URL and hash

`kind = "sun.irradiance"` becomes resolvable the way the data catalog already resolves
assets: a short name for the canonical library, or a URL (GitHub release, OCI image, wasm
file) locked by content hash in the project. A canonical library of first-party modules
lives in its own repo. Third parties publish theirs anywhere. The wiki's engines shelf can
list zoo modules alongside everything else, since it already carries `tool.tier`,
`open.*` and provenance. "Zoo" is his word and should stay; "wrapper" is one kind of zoo
animal, a module whose body is someone else's engine.

### 3. `describe()`: modules declare their surface

Add one verb. A module returns a description: parameters with types, units and defaults;
topics published and subscribed; fields owned and read, with units; ledgers and accounts
touched; data assets needed (catalog keys); time step; provenance notes (which numbers are
guesses). Consequences, all immediate:

- `esim check manifest.toml` validates wiring before running: every subscription has a
  publisher, every field read has an owner, every ledger has a closer, every asset is in
  the catalog, units agree at seams.
- `esim kinds --json` is the toolchain's surface for an LLM, generated and always current.
  The English-to-manifest facade reads this, not documentation.
- The wiki can render module cards from it.

### 4. Two grammars, named

- **High-level grammar: the manifest.** Place (once), window, seed, cadence, modules by
  reference with parameters, what-ifs as dated diffs, outputs wanted. A document a person
  or an LLM writes. Unreal's blueprint, in his analogy.
- **Low-level grammar: inside a module.** Rust, Fortran via BMI, Python, wasm, anything
  that speaks the protocol. Where the maths lives. Nobody composes at this level unless
  they want to.
- **Between them: the vocabulary.** Topic names, field names and units, ledger names,
  cell addressing. This is the real interoperability surface and the thing to govern
  carefully. It is also exactly what the wiki's Ontologies shelf is for.

On BMI (CSDMS Basic Model Interface, 2.0, Hutton, Piper and Tucker 2020): his reading is
right. It is `initialize`, `update`, `get_value`, `set_value` and grid metadata for
stepped process models on grids, meshes or points. No events, no populations, no
ledgers. So it is not a rival to the bus; it is one adapter at the low level: a module
whose `handle(tick)` calls the wrapped model's `update` and exchanges fields through the
World store. Worth adopting for the engines that speak it, and nothing more.

### 5. Data: the wiki is the index, the store holds the bytes

The wiki already has what is needed: `data-sources/` entries with YAML frontmatter
(`datasource.homepage`, `open.*`, `provenance`), an `events/` folder, and a
machine-readable mirror under `/m/`. So:

- **Index of sources** lives on the wiki. Each data-source entry gains the fields the
  registry needs: fetch recipe (URL pattern), format, licence, resolution, extent,
  update cadence, schema. The simulator's `data/catalog.toml` becomes a per-project lock
  of what was used, pulled from the wiki's `/m/` mirror, not a hand-kept duplicate.
- **Bytes** live in the content-addressed store (today `data/cache/`, later R2), shared
  by every project and every user, written once.
- **Future events and black swans** live on the wiki as entries with provenance, which is
  where their checking belongs; the simulator pulls them as tables. The nine speculative
  rows from the photographed book table and every "check" row would be visible and
  correctable there instead of buried in a TOML file.
- **Citations** are already the wiki's native form.

This also answers "where should shared data resources live" in a way that is not a
product: it is an encyclopedia with a machine mirror, and anyone's tool can read it.

### 6. Scenarios as the guiding light

A `scenarios/` folder, one file each: the question in a person's words, the place, the
horizon, the outputs wanted, the modules and data it needs, the validation available, its
status (imagined, runnable, validated). Harvested from the brief's worked chains (Gulf
hypoxia, food system), the wiki's use cases and vitals page, AnyLogic's and NetLogo's
galleries, and the requests he has already voiced ("traffic in my town with changes to
speed limits", Hormuz, a parcel, a western fire basin). Each milestone from here takes a
scenario, not a capability, and the facade is scored on how many scenarios it can turn
into a valid manifest without a person. The fitness matrix stays as the capability view.

## On the speedrun

Agreed that the harness, the zoo contract and the facade can be world class in weeks; the
tools available now make that plausible and the overnight ladder is evidence. The one
thing that cannot be sped up is calendar time for verification: a river forecast is checked
when the river arrives, a crop model when the season ends. Build the hindcast harness so
that most verification is against the past and only the last mile waits on the future.

## What to do first

Nothing of this needs a rewrite. In order: `describe()` and `esim check`; place once in
the manifest; the protocol document and a stdio module host with one module moved out of
process to prove it; module references by URL and hash; the scenarios folder seeded from
what exists; then the data-source fields on the wiki, which is a twin-compendium change
and the wiki room's to make. His call where to start.
